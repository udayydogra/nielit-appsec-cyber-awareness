# NIELIT AppSec + Cyber-Awareness Training Platform
## A Comprehensive Engineering and Design Report

**Prepared for:** National Institute of Electronics & Information Technology (NIELIT), Ministry of Electronics and Information Technology (MeitY), Government of India

**Subject:** A bilingual, self-hosted, security-training platform that teaches application-security exploitation and public cyber-fraud awareness through hands-on, server-scored laboratories.

---

## Abstract

This report documents, in full, the design and construction of a single-server security-training platform built for NIELIT. The platform pursues two educational missions inside one coherent product. The first mission is offensive application-security training: it lets a learner reproduce real web vulnerabilities — SQL injection, cross-site scripting, insecure direct object references, server-side request forgery, command injection and more — against deliberately vulnerable targets that are isolated well enough to be safe on a shared machine. The second mission is public cyber-fraud awareness: it walks ordinary citizens through the most common Indian digital scams — the "digital arrest" video call, UPI collect-request fraud, KYC-update phishing, SIM-swap and OTP theft — as branching, decision-driven stories rendered inside a realistic phone simulation. Both missions are delivered bilingually, in English and Hindi, at every leaf of content, and both are scored on the server so that a certificate can never be forged from the browser.

The entire system is engineered to run within a modest five-gigabyte virtual machine, which shaped nearly every architectural decision recorded in this document, from the tiered execution model that reserves real containers only for the exercises that truly need them, to the choice of a small local language model for the built-in AI mentor, to the aggressive reaping of ephemeral containers the moment a learner leaves a lab. The report describes the technology stack in detail, the data model and the deny-by-default authorization system, the container lifecycle and its hardening, the interactive in-browser terminal, the AI mentor, the content-manifest system and the in-application authoring tools, the complete catalogue of laboratories, the front-end application and its design language, and finally the operational, security and performance considerations that hold the whole thing together. It closes with a narrative history of the engineering decisions that produced the current state of the codebase.

# Part I — Overview

## Chapter 1. Introduction and Vision

Security education has a persistent gap between what is taught and what is retained. A lecture on SQL injection can explain, accurately and completely, that concatenating user input into a query allows an attacker to change the meaning of that query; and yet a student who has only heard the explanation rarely develops the instinct that a practitioner needs. The instinct comes from doing the thing: from typing an apostrophe followed by `OR '1'='1` into a login form, watching the authentication melt away, and feeling the small shock of having bent a system to one's will. The same is true, in a different register, for the ordinary citizen who is told that "you should never share an OTP." The advice is correct and universally repeated, and it fails constantly, because the moment of the scam does not feel like the moment in the poster. It feels like a frightened phone call from someone who claims to be a police officer, at a time when the victim is tired and alone, and the pressure is engineered specifically to override the remembered advice. Knowledge that is not rehearsed under something resembling the real conditions tends not to survive contact with those conditions.

This platform was built on the conviction that both audiences — the aspiring application-security professional and the ordinary citizen — learn far more durably by rehearsing the real situation than by reading about it. For the security professional, that means running genuine exploits against genuinely vulnerable software, in a sandbox, and being scored by the server on whether the exploit actually worked rather than on whether a multiple-choice answer was selected. For the citizen, it means being placed inside a convincing reconstruction of a scam, being forced to choose what to do at the exact decision point where real victims choose wrongly, and then being shown the consequence of that choice with the specific manipulation technique named and explained. The platform therefore treats "learning by doing" not as a slogan but as the organising principle of its entire architecture.

A second conviction shaped the work: that a training platform intended for a national institute serving a linguistically diverse country cannot treat Hindi as an afterthought bolted onto an English product. Every piece of learner-facing content in the system — every lab title and summary, every lesson paragraph, every scenario line, every quiz question and answer choice, every mission and hint — carries both an English and a Hindi rendering, stored side by side, and the interface switches between them instantly without reloading. This is not a translation layer applied at the edges; it is a data shape carried at every leaf of the content model. The consequence is that the platform reads as a genuinely bilingual product rather than an English product with a Hindi option, which matters a great deal for the awareness content in particular, because the citizens most vulnerable to the scams the platform teaches are frequently more comfortable in Hindi than in English.

A third conviction, more prosaic but no less consequential, was that the platform had to be cheap to run. The target deployment was a single virtual machine of roughly five gigabytes of memory — the sort of modest allocation an institute can stand up without a procurement battle. This constraint is the hidden protagonist of much of this report. It is the reason the platform does not spin up a container for every exercise, the reason it uses a small quantised language model rather than a large one for its offline mentor, the reason ephemeral containers are reaped the instant a learner walks away, and the reason the front-end bundle is aggressively code-split so that the heavy machinery of the interactive terminal is never downloaded by a learner who only wants to read a lesson. A more generous budget would have permitted a lazier architecture; the tight budget forced a set of decisions that, in the end, produced a cleaner and more defensible system than a generous budget likely would have.

## Chapter 2. Objectives, Audience and Scope

The platform serves three kinds of people, and the design distinguishes them carefully. The first is the learner, who is either a student of application security working through the offensive labs, or a citizen — or a trainee being sensitised on behalf of citizens — working through the awareness scenarios. The learner needs the content to be engaging, the exercises to be genuinely interactive, the feedback to be immediate and specific, and the whole experience to be available in the language they think in. The second kind of person is the instructor, who is responsible for a batch of learners and needs to be able to see how that batch is progressing without being able to reach into the data of learners outside their remit. The third is the administrator, who provisions accounts, forms and retires batches, and authors or curates the training modules themselves. Each of these roles is expressed in the platform's authorization model as a distinct bundle of permissions, and the system is careful never to let one role silently acquire the powers of another.

The scope of the application-security curriculum is deliberately broad, covering the vulnerability classes that a working practitioner is most likely to encounter and that a hiring interview is most likely to probe. It includes the classic injection family — SQL injection and operating-system command injection — alongside the access-control failures that dominate real-world breach reports, namely insecure direct object references and broken object-level authorization on APIs. It covers cross-site scripting and cross-site request forgery, the two canonical browser-trust failures; broken authentication and weak session management; server-side request forgery and XML external entity injection; insecure deserialization and path traversal; insecure file upload; business-logic flaws and race conditions; the modern concerns of API security and of prompt injection against language-model features; and a cloud-security exercise that models a misconfigured object store and over-permissive access policy. Alongside these hands-on exercises sit a set of content-driven labs that a practitioner cannot "exploit" in a console but must understand nonetheless: secure code review, threat modelling, incident response, and passive reconnaissance.

The scope of the awareness curriculum is drawn from the fraud landscape that Indian citizens actually face. It includes the "digital arrest" scam, in which a caller impersonating the police or the Central Bureau of Investigation uses a video call to terrify a victim into transferring money to "clear their name"; UPI payment fraud built on the collect-request mechanism, in which a scammer posing as a buyer sends a request that debits rather than credits the victim; the KYC-update scam; banking fraud built on a fake "card blocked" call and OTP theft; SIM-swap and OTP-sharing; courier and customs parcel scams; fake customer-care numbers paired with remote-access applications; fake job offers and task scams; deepfake and AI voice-clone scams; QR-code payment fraud; phishing across email, SMS and WhatsApp; social-media impersonation and romance scams; and the more foundational topics of password security and multi-factor authentication, mobile security against malicious application packages, digital privacy around permissions and public Wi-Fi, and general cyber hygiene around updates, backups and reporting.

What is explicitly out of scope is as important as what is in it. The platform does not attempt to be a full offensive-security range with a Kali desktop, a suite of professional tooling, and arbitrary network access; that ambition is incompatible with a five-gigabyte budget and, more importantly, with running safely on shared infrastructure. Instead it provides just enough of a real environment — a genuine shell inside a genuinely isolated container for the exercises that need one, and faithful simulations for the exercises that do not — to teach the concept without importing the operational and security burden of a real range. The report returns to this trade-off repeatedly, because it is the single most important design decision in the system.

## Chapter 3. The System at a Glance and the Tiered Execution Model

At the highest level the platform is a small number of cooperating processes. A single-page web application, written in React and served as static files, runs in the learner's browser and constitutes the entire user interface. A back-end service, called the lab manager, written in TypeScript and running on Node, holds all the authority: it authenticates users, enforces permissions, serves content, grades quizzes, issues certificates, drives the AI mentor, and — for the exercises that need it — spawns and destroys isolated containers and bridges a terminal into them. Behind the lab manager sit two data stores: a PostgreSQL database that holds the durable state of the system, and a Redis instance that holds the fast, ephemeral state such as container slots, heartbeats and rate-limit counters. For the exercises that require a live environment, the lab manager shells out to the host's Docker daemon to run short-lived target containers. An optional local language-model server can be run alongside the rest when no external model provider is configured, so that the AI mentor works even on an air-gapped machine.

The organising abstraction that ties the content to this infrastructure is the tiered execution model. Not every exercise needs the same amount of machinery, and providing a live container for an exercise that could be taught with a static page would be both wasteful and, on a shared machine, needlessly risky. The platform therefore classifies every laboratory into one of four execution tiers, and the tier determines how much of the infrastructure is engaged when a learner enters it.

Tier zero is pure content. These are the labs — secure code review, threat modelling, incident response, reconnaissance, and the entire awareness curriculum — that teach through reading, animation, decision-making and quizzes, and that require no server-side execution environment at all beyond the ordinary serving of their content and the grading of their quizzes. A tier-zero lab consumes essentially no resources beyond a database row or two of progress.

Tier one is simulation. A tier-one lab, of which the cloud-security exercise is the example, presents what looks like a command-line interface or an external service but is in fact a deterministic mock implemented on the server. The learner issues commands and receives realistic responses — a listing of a public storage bucket, the output of an over-permissive access policy — without any real cloud account or real external system being involved. The simulation is convincing enough to teach the concept and cheap enough to run for every learner simultaneously.

Tier two is the shared vulnerable application. This is the workhorse tier for the application-security curriculum, and it embodies the platform's central safety trick. A tier-two lab runs a single, deliberately vulnerable piece of logic on the server — an injectable login query, an object-fetching endpoint that forgets to check ownership, a guestbook that stores comments without escaping them — but it partitions the data by owner so that each learner only ever attacks their own seeded rows. The vulnerability is entirely real: a learner's tautology genuinely subverts the query, their union-based injection genuinely exfiltrates additional columns, their direct-object-reference genuinely returns another persona's invoice. But because the data is scoped to the learner's own identity, the exploit can never reach another real learner's information. One hardened application, contained per-user by an ownership boundary, safely teaches a genuine attack to an entire cohort at once, and a reset function restores each learner's sandbox to its initial state on demand.

Tier three is the ephemeral container. A handful of exercises — command injection, server-side request forgery, XML external entity injection, insecure deserialization and path traversal — cannot be taught convincingly without giving the learner a real shell in a real, if minimal, environment. For these, and only these, the lab manager runs a genuine Docker container per learner, hardened to the point of near-uselessness for anything but the intended lesson. The container has no network access, a read-only filesystem, every Linux capability dropped, a tight memory and process-count limit, and a small writable temporary space; in production it is run under a stronger sandbox runtime for defence in depth. The learner is given an interactive shell inside this box through the browser, reads the flag that proves they achieved code execution, and — crucially — the container is destroyed the moment they leave, so that the five-gigabyte machine is never carrying more than a small, bounded number of these boxes at once.

The elegance of the tiered model is that the content author does not think about infrastructure at all. They declare, in the lab's manifest, which tier the lab belongs to, and the platform arranges the rest: it serves a tier-zero lab as content, runs a tier-one lab's simulation, resets a tier-two lab's per-user sandbox on entry, or spawns and later reaps a tier-three container. The tier is a property of the content, and the infrastructure follows from it. This is what allows a single modest machine to host thirty-eight laboratories spanning four very different execution models without ever running more heavy machinery than the exercises currently in use actually require.

# Part II — Architecture and Foundations

## Chapter 4. High-Level Architecture

The architecture is deliberately conventional at its skeleton and unconventional only where the problem demanded it. A browser loads a static single-page application. That application speaks to the lab manager over HTTP for everything transactional — logging in, fetching the catalogue and individual lab manifests, submitting quiz answers, asking the mentor a question, and, for administrators, managing users, batches and modules — and over a WebSocket for the one thing that HTTP cannot do well, which is stream an interactive terminal session. The lab manager is stateless with respect to the browser in the sense that every request carries its own authentication in a signed cookie and is authorized on its own merits; there is no server-side session store that the browser depends upon beyond the durable stores themselves.

Those durable stores are two, chosen for their different temperaments. PostgreSQL holds everything that must survive a restart and that benefits from relational integrity and transactional guarantees: users and their roles, the permission catalogue and its grants, cohorts and their memberships, the telemetry event stream, quiz answer keys, scores, progress, certificates, the audit log, the per-user data for each tier-two laboratory, and the admin-authored modules. Redis holds everything that is fast and disposable and whose loss on a restart is acceptable or even desirable: the record of which learners currently hold a live tier-three container slot, the heartbeats that keep those slots alive, and the counters that rate-limit expensive operations. The division is the standard one — durable relational truth in Postgres, fast ephemeral coordination in Redis — and the platform does not fight it.

The one genuinely unusual limb of the architecture is the path from the browser terminal to a container shell. When a learner enters a tier-three lab, the front-end opens a WebSocket to the lab manager. The lab manager authenticates that upgrade request from the very same signed cookie that authorizes every other request — it never trusts an identity supplied in the WebSocket payload — and then checks that the learner actually owns a running container for the lab in question, which structurally prevents one learner from attaching to another's box. Having authorized the connection, the lab manager allocates a real pseudo-terminal on the host and runs a shell inside the learner's container attached to that pseudo-terminal, then bridges bytes in both directions between the WebSocket and the pseudo-terminal. The learner's keystrokes travel from the browser terminal emulator, across the WebSocket, into the pseudo-terminal, and are handled by a genuinely interactive shell; the shell's output travels back the same way and is painted into the browser. Because a real pseudo-terminal is involved, the shell behaves like a real shell — tab-completion, command history, arrow-key line editing and interrupt handling all work — rather than like the crippled line-at-a-time interface that a naive pipe would produce.

The whole assembly is packaged as a set of containers orchestrated by Docker Compose: the lab manager, the database, the Redis instance, the web server that serves the static front-end, and — behind an optional profile — the local language-model server. The lab manager container is given access to the host's Docker socket so that it can spawn the tier-three target containers as siblings on the host rather than as nested containers, which is both more efficient and more secure than the alternative. Everything is sized with explicit memory limits so that the sum of the parts fits comfortably inside the five-gigabyte envelope with room to spare for the transient tier-three boxes.

## Chapter 5. The Technology Stack in Full

The back-end service is written in TypeScript and executed on Node. It is authored as native ECMAScript modules under Node's modern module resolution, which is why its internal imports carry explicit file extensions; this is a small but pervasive discipline that the codebase observes consistently. The web framework is Express, chosen for its ubiquity, its minimalism and the ease with which its middleware model expresses the platform's deny-by-default authorization as a single gate through which every protected route passes. Password hashing uses bcrypt, a deliberately slow adaptive hash that resists brute-force attack. Sessions are carried in signed JSON Web Tokens set as HTTP-only cookies, so that the browser cannot read or tamper with them from script. Cookies are parsed by the standard cookie-parser middleware, and cross-origin requests during development are permitted from the known development origins by the standard CORS middleware while being locked down in production.

Data access to PostgreSQL uses the node-postgres client directly, through a thin wrapper that exposes parameterised query helpers and nothing else; there is deliberately no object-relational mapper in the system, both to keep the dependency surface small and to keep the SQL visible and auditable, which matters especially in a platform whose whole subject is injection. Redis access uses the ioredis client. The WebSocket server for the terminal uses the ws library. The interactive terminal's server side depends on node-pty, a native addon that allocates real pseudo-terminals; this is the one native dependency in the back-end, and its presence dictated a specific arrangement of the container build so that the addon is compiled once, against the container's Node version, and carried into the runtime image without dragging a full compiler toolchain along with it.

The front-end is a React application built and bundled by Vite. It is written in TypeScript throughout. Its styling combines Tailwind's fourth-generation engine, wired in through Vite, with a substantial hand-authored stylesheet of design tokens and component styles that gives the platform its specific governmental look rather than the generic look that unadorned utility classes tend to produce; the Tailwind layer principally supplies a consistent reset and the occasional utility, while the semantic classes in the hand-authored stylesheet carry the actual design. Icons come from the Lucide icon set, chosen for its breadth, which allowed every one of the thirty-eight laboratories to be given a distinct, on-theme glyph rather than a generic one. The in-browser terminal emulator is xterm.js together with its fit addon, which sizes the terminal to its container. Typography uses Roboto and Roboto Condensed for the Latin script alongside a Devanagari face for Hindi, so that both languages render with intent rather than with a fallback.

The data tier is PostgreSQL for durable relational state and Redis for ephemeral coordination, both run as official Alpine-based images sized with memory limits. The container runtime is Docker, driven from the lab manager over the host socket, with an aggressively hardened configuration for the tier-three target images and, in production, a stronger sandbox runtime layered on top. The optional local language model is served by Ollama running a small quantised model, chosen specifically so that the mentor can function on an air-gapped, memory-constrained machine without any external dependency. Orchestration across all of these is Docker Compose. The whole stack was chosen with two consistent biases: prefer small, well-understood, widely-supported components over large frameworks, and prefer components that can run entirely offline over components that assume a connection to a cloud service.

## Chapter 6. The Data Model and Database Design

The database schema is organised into a small number of clearly-separated concerns, and its design philosophy is stated at the top of the schema itself: authorization grants are stored as data rather than expressed as code, so that changing what a role can do is a data change rather than a code change. This principle radiates through the identity and access-control tables and is worth understanding first, because it explains why the schema looks the way it does.

Identity begins with a users table. Each user has a stable universally-unique identifier as a primary key, a unique email address, a bcrypt password hash — never a plaintext password, a discipline the schema comments insist upon — a display name, and a preferred locale of either English or Hindi. To support the account lifecycle that administrators require, each user also carries a status that is either active or deactivated, together with the timestamp at which they were deactivated; this is what allows an administrator to suspend an account reversibly before deciding whether to delete it permanently, and it is what the login path consults to refuse entry to a deactivated account.

Access control is expressed through four tables that together implement additive role-based access control. A roles table names the roles — student, trainee, instructor and administrator. A permissions table names the fine-grained permissions, each a verb-like string such as the permission to access a lab, to tune the mentor's prompt, to manage users, to assign roles, to assign learners to cohorts, or to edit modules. A role-permissions join table records which permissions each role grants, and a user-roles join table records which roles each user holds. Because roles are additive and permissions are looked up through the roles a user holds, a user's effective set of permissions is simply the union of the permissions granted by all their roles, computed with a single query at the moment their session is established. Nothing in the application code hard-codes what a role can do; the code asks only whether a user holds a particular permission, and the answer is assembled from these tables.

Cohorts model the NIELIT batch, which is the scope boundary around which the instructor role revolves. A cohorts table names each batch and, like users, carries a status that is either active or suspended together with a suspension timestamp, so that a batch can be suspended once its course concludes without being deleted. A cohort-members join table records which users belong to which cohort and in what capacity, either as a learner or as an instructor assigned to oversee the batch. This membership is the raw material from which the instructor's scope is computed: an instructor may see the learners in the cohorts they are assigned to, and no others.

The remaining tables serve the learning machinery. A single events table is the telemetry spine for both the application-security and the awareness curricula; every meaningful moment — a lab started, an exploit attempted, an exploit succeeded, a decision made, a quiz answered, a node completed, a lab completed, a hint requested — is recorded as one row with a user, a lab, an event type, an optional node identifier, an outcome and a free-form payload, and these events are only ever written by the server. A quiz-keys table holds the correct answers to quiz questions, kept strictly on the server and never shipped to the browser, so that grading is authoritative. A scores table records each learner's score and maximum possible score per lab. A progress table records which nodes or steps a learner has completed per lab, along with a small blob of state. A certificates table records the system-issued, cryptographically-signed certificates, one per learner per lab, each carrying a signature computed over a canonical representation of its contents so that it can be verified by anyone without trusting the presenter. An audit-log table records every privileged write and every cross-user read, capturing the actor, the action, the target and a detail payload, so that administrative activity leaves a durable trail.

Two further groups of tables support the content. The tier-two laboratories each own a table of per-user data, partitioned by an owner identifier that is the linchpin of the multi-tenant safety model — the injectable accounts table for the SQL-injection lab, the per-user invoices for the direct-object-reference lab, the raw-stored comments for the stored-cross-site-scripting lab, and so on for every tier-two exercise. Each such table exists precisely so that the deliberately vulnerable query can be genuinely vulnerable while remaining confined to the attacking learner's own rows. Finally, a modules table and a module-settings table support the administrator's ability to author new laboratories inside the application and to enable, disable or reorder any laboratory, whether built-in or authored; the authored modules are stored as complete content manifests in a JSON column, and the settings table carries a visibility-and-ordering overlay keyed by module identifier that applies uniformly to built-in and authored modules alike.

The schema is applied to a fresh database at initialisation, and subsequent structural changes are captured as idempotent migrations that can be run against an existing database without disturbing the data already in it — a discipline that became important the moment the platform had real state to preserve, because the initialisation scripts only ever run against an empty data volume.

## Chapter 7. Identity, Authentication and Session Management

The platform's handling of identity rests on a single principle that it never violates: identity is derived from a signed session, never from anything the client can set freely. A request does not get to say who it is by putting a user identifier in a header or a URL; if it could, then a learner who changed that identifier would impersonate another learner, and every access-control check in the system would be worthless. Instead, identity travels in a signed token that the client cannot forge, and the server re-derives the acting user from that token on every request.

Authentication proper happens at the login endpoint. The learner submits an email and a password. The server looks up the user by the lower-cased email, and compares the submitted password against the stored bcrypt hash. The comparison is written so that the response is the same whether the user does not exist or the password is merely wrong, so that the endpoint does not become an oracle that reveals which email addresses are registered. If the credentials are valid, the server additionally refuses the login if the account has been deactivated, returning a distinct message in that case so that a suspended learner understands why they cannot enter. On success, the server issues a session and returns the full authenticated user — not merely the identity, but the roles and the effective permissions as well — so that the front-end can immediately decide what to show, in particular whether to reveal the administrative area, without a second round-trip. This last detail was the subject of a specific bug and its fix during development, recounted later in the history chapter, because an earlier version returned only the bare identity and the front-end crashed when it later assumed the permissions were present.

The session itself is a JSON Web Token signed with a server secret and carrying the user's identifier and email, with a fixed expiry. It is set as an HTTP-only cookie so that browser script cannot read it, with the same-site attribute set to limit its transmission on cross-site requests, and with the secure attribute enabled in production so that it is never sent over an unencrypted connection. On every request, a session middleware reads this cookie — or, as an alternative for tooling, a bearer token in the authorization header — verifies its signature, and, if valid, loads the corresponding user from the database along with their current roles and permissions, attaching the resulting authenticated-user object to the request for the rest of the pipeline to consult. Because the roles and permissions are loaded fresh on each request rather than baked into the token, a change to a user's roles takes effect on their next request rather than requiring them to log in again, and a deactivated user's subsequent requests can be refused even if they still hold a valid token.

Self-service account management is deliberately narrow and strictly self-scoped. A learner may change their display name and their preferred locale, and may change their password by supplying the current password and a new one; the password change verifies the current password before accepting the new one, and the whole flow is scoped to the identity in the session so that there is no user identifier in the URL for anyone to tamper with — the endpoint structurally cannot be aimed at another account. Logging out simply clears the cookie. There is no self-service registration; accounts are provisioned by administrators, which suits an institutional deployment where enrolment is controlled rather than open.

## Chapter 8. Authorization: Roles, Permissions and Scopes

If authentication answers the question of who is making a request, authorization answers the question of whether they are allowed to do what they are asking. The platform answers it with a deny-by-default system that checks permissions rather than roles and, where a request reaches across users, additionally checks scope. Both checks flow through a single piece of middleware, which is the one enforcement point that every protected route in the system passes through, and this concentration is itself a security property: there is one place to reason about, one place to audit, and no scattered, ad-hoc checks to forget.

The first half of the check is the permission gate. Every protected route declares the permission it requires. The middleware consults the acting user's effective permissions — the union computed from their roles — and, if the required permission is absent, refuses the request and writes an audit record of the denial. The deliberate choice to check permissions rather than roles is what makes the system's grants live in data: a route does not say "administrators only," it says "requires the permission to manage users," and whether a given role carries that permission is a fact stored in the database. This means the powers of a role can be adjusted without touching the code, and it means a new role could be introduced with a bespoke bundle of permissions without any route needing to learn about it.

The second half of the check is the scope gate, which matters whenever a request concerns a particular user rather than the actor themselves. Holding the permission to monitor a cohort does not entitle an instructor to monitor every learner in the system; it entitles them to monitor the learners within their assigned cohorts. The middleware therefore supports a set of scope resolvers. The self scope confirms that the target of a request is the actor themselves, which is how self-service endpoints are protected structurally. The cohort scope confirms that the target user shares a cohort that the actor is entitled to oversee, which is how an instructor's reach is confined to their batches. A third resolver, the container-ownership scope, is used by the tier-three machinery to confirm that a learner attaching to a terminal or stopping a container actually owns the container in question, which is the anti-tampering boundary that prevents one learner from reaching into another's live box. When a scoped request succeeds against a target that is not the actor, that cross-user access is itself audited, so that the trail records not only administrative writes but also legitimate cross-user reads.

This two-stage design — permission first, then scope — is what the codebase's own comments call the anti-broken-object-level-authorization layer, named after the very vulnerability class that one of the labs teaches. It is a pointed piece of self-consistency: a platform that teaches learners to exploit missing ownership checks is itself built so that ownership checks are centralised, mandatory and impossible to forget, because they live in the one gate that every request must pass. The permission catalogue that this system draws upon is broad and forward-looking, naming not only the permissions the current features exercise but also permissions for capabilities the platform is designed to grow into, such as tuning the mentor's prompt, uploading datasets, managing localisation, switching the model provider and issuing certificates; the full catalogue is reproduced in an appendix.

# Part III — The Backend Service

## Chapter 9. The Lab Manager: Structure and Request Lifecycle

The lab manager is a single Express application whose composition is easy to describe and whose discipline is in the details. At startup it installs a small stack of middleware: a JSON body parser with a modest size limit so that no request can exhaust memory by sending an enormous body, the cookie parser, the cross-origin policy, and the session middleware that attaches the authenticated user. It then mounts a handful of routers, each owning a coherent slice of the surface: the authentication router for login, logout and the current-user endpoint; the labs router for the catalogue, individual manifests, tier-two exploit endpoints, quiz submission, and the tier-three container lifecycle; the self-service router for a learner's own scores, certificates, progress, profile and password; the mentor router for the AI mentor; and the administrative router for user, batch and module management. Two endpoints sit outside the routers because they must be reachable without authentication: a health check that confirms the database and Redis are reachable and reports which mentor provider is active, and the public certificate-verification endpoint that lets anyone confirm a certificate's authenticity from its identifier alone.

Every asynchronous route handler is wrapped so that a rejected promise becomes a clean error response rather than an unhandled rejection that could destabilise the process, and a final error-handling middleware turns any escaped error into a five-hundred response instead of a crash. This matters more than it might seem, because the platform runs untrusted-ish operations — spawning containers, bridging shells — and a single unhandled rejection in a fire-and-forget path must never be allowed to take down the service for every learner. The process additionally installs last-resort handlers for unhandled rejections and uncaught exceptions that log rather than exit, and a graceful-shutdown routine that, on receiving a termination signal, stops the container reaper, closes the server, and drains the Redis and database connections before exiting.

At boot the lab manager validates all of its built-in content manifests, failing fast and loudly if any content file is malformed, on the principle that a content error should be caught at deployment rather than discovered by a learner. Having loaded the built-in content, it then pulls any administrator-authored modules out of the database and folds them into the same in-memory content cache, so that from that point on the rest of the system cannot tell whether a given lab came from a file on disk or a row in the database; this uniformity is what allows authored labs to be served, mentored and, where applicable, containerised through exactly the same code paths as the built-in ones. Finally it starts the container reaper on its interval and begins listening, and separately attaches the WebSocket terminal transport to the same underlying server so that the terminal shares the service's port and authentication.

The request lifecycle for a typical protected operation is therefore uniform and predictable. A request arrives carrying its session cookie. The session middleware verifies the cookie and attaches the acting user with their roles and permissions. The route's permission gate confirms the required permission and, where relevant, the scope resolver confirms the actor's reach over the target. The handler runs, reads or writes the database with parameterised queries, emits any telemetry, writes an audit record if the operation was privileged, and returns. There is no step in this sequence that trusts a client-supplied identity, and there is no privileged operation that escapes the audit trail. The regularity is the point: the same shape repeats across the whole surface, which is what makes the system tractable to reason about despite the breadth of what it does.

## Chapter 10. Telemetry, Scoring and Certificates

The platform is emphatic that outcomes are decided by the server, and the telemetry, scoring and certificate subsystems are where that emphasis becomes concrete. The browser sends actions — it says that a login was attempted with a particular payload, that a quiz was submitted with particular answers, that a decision was taken in a scenario — but it never sends outcomes. It does not say "I scored eighty per cent" or "I passed"; it says what it did, and the server decides what that means. This inversion is the difference between a training platform whose certificates mean something and one whose certificates are a formality that any learner could fabricate from the browser console.

Telemetry is a single append-only stream. Whenever something meaningful happens, the server writes one event describing it: the actor, the lab, the kind of event, an optional finer-grained node identifier for scenario steps, an outcome classification, and a payload with whatever structured detail is useful. Because the stream is unified across both curricula, the same analytics can describe a learner's journey through an injection lab and through a fraud scenario, and because it is written only by the server, it cannot be inflated by a learner reporting achievements they did not earn. The stream is the raw material from which progress and, ultimately, cohort-level reporting are derived.

Scoring rests on the separation of questions from their answers. A quiz as authored, and as shipped to the browser, contains only prompts and answer choices; the correct choices live in a server-side table and are never transmitted. When a learner submits their answers, the server compares them against the held keys, computes the score and the maximum possible score, records the result, and returns to the learner which questions they got right — but never the answers to the ones they got wrong, so that the quiz is not turned into an answer key by repeated submission. For authored modules, this same discipline is preserved by a subtle mechanism: the in-application authoring tool lets an administrator mark the correct choice for each question, but on save the server strips those correct-answer markings out of the manifest it stores and shipped, and writes them instead into the server-side key table; when the administrator later reopens the module to edit it, the keys are re-attached for their eyes only. A learner fetching an authored lab therefore receives exactly the same key-free content that they would for a built-in lab.

Certificates are the durable, verifiable proof of achievement, and they are constructed to be trustworthy in the hands of a stranger. When a learner earns a certificate by completing a lab's assessment, the server issues one — idempotently, so that completing the same lab twice does not mint a second certificate — and signs it with a keyed hash computed over a canonical representation of its contents. The certificate is then verifiable through a public endpoint that takes only the certificate's identifier and confirms, or denies, that the signature is authentic. This means a certificate can be shown to a prospective employer or an examining body who can verify it themselves, without the platform having to expose any learner's private data and without the verifier having to trust the person presenting the certificate. The signature is the guarantee; the public endpoint is the means of checking it; and because the signing key never leaves the server, a certificate cannot be forged even by someone who understands exactly how the scheme works.

## Chapter 11. The Container Lifecycle and Tier-3 Isolation

The tier-three laboratories are where the platform does its most delicate work, because they give a learner a real shell in a real environment on a shared machine, and they must do so without ever letting that power escape the intended lesson or exhaust the host. The container lifecycle is therefore engineered around two anxieties in equal measure: that a container might do something it should not, and that too many containers might exist at once. Both anxieties are answered by a combination of aggressive hardening and aggressive reaping.

When a learner enters a tier-three lab, the lab manager attempts to claim a slot for them. The slot mechanism is a global concurrency limit expressed in Redis: only so many live containers may exist across the whole platform at once, and a learner arriving when the limit is reached is queued rather than served, so that the host can never be driven into memory exhaustion by a rush of simultaneous entrants. Having claimed a slot, the lab manager checks whether the learner already has a running container for this lab and reuses it if so — re-entry is idempotent — and otherwise runs a fresh one. The container is run from a minimal image specific to the lab, and it is run with a configuration that strips away nearly everything a container can normally do. It is detached and set to be removed automatically when it stops. Its memory is capped tightly and its swap is capped to the same figure so that it cannot spill into swap to evade the limit. Its process count is capped so that it cannot fork-bomb the host. Its filesystem is read-only, with only a small, non-executable temporary space mounted writable so that ordinary commands that need scratch space still work while the learner cannot persist or execute arbitrary files. Every Linux capability is dropped. Its network is disabled entirely, so that server-side request forgery and data-exfiltration attempts have nowhere to go, which is both a safety measure and, for the relevant labs, part of the lesson. In production a stronger sandbox runtime is layered underneath so that even a kernel-level escape has another barrier to cross. The container is labelled with the owning learner and the slot so that it can be found and reaped later.

The reaping is as important as the spawning. A learner is expected to send a heartbeat while they remain in the lab, and the reaper runs on an interval, sweeping for containers that have been idle beyond a threshold or alive beyond a maximum lifetime and destroying them, freeing their slots. This is the safety net that guarantees the host is never carrying stale boxes: even if a learner closes their laptop mid-exercise, their container will be reaped when its idle timeout elapses. On top of this timed safety net, the front-end takes care to stop the container explicitly the moment the learner leaves the workspace, so that in the ordinary case the box is gone within a second of the learner exiting rather than lingering until the reaper notices. The interplay between the explicit stop and the timed reap was the subject of a specific and instructive bug during development, described in the history chapter, in which the front-end's fire-and-forget start and stop calls could race against one another under a particular development-mode behaviour and leave an orphaned container that the slot-based reaper would not catch; the fix was to make the workspace start the container exactly once per session and to defer the stop so that it always runs after the start has completed, which closed the race.

The net effect of all this machinery is that a five-gigabyte machine can offer a genuine, interactive, code-execution laboratory to a bounded number of learners at a time, safely, because each container is nearly inert except for the intended lesson, because their number is capped, and because they are destroyed the instant they are no longer needed. The learner experiences none of this; they see a terminal, they run their exploit, they read their flag, and they leave. The complexity is entirely on the platform's side, which is exactly where it belongs.

## Chapter 12. The Interactive Terminal Subsystem

The terminal is the seam between the browser and the container shell, and it is engineered to feel like a real terminal because a crippled one would undermine the very realism that the tier-three labs exist to provide. On the browser side, the terminal is the xterm.js emulator, sized to its window and themed to match the workspace. On the server side, the terminal is a real pseudo-terminal wrapping a shell inside the learner's container. Between them runs a WebSocket carrying a small, well-defined protocol.

The authorization of the terminal connection deserves emphasis because it is where a careless implementation would introduce a serious vulnerability. The WebSocket upgrade request is authenticated from the same signed session cookie as every other request; the terminal never accepts an identity supplied in the connection itself. Having established who the learner is, the server confirms that they own a running container for the lab named in the connection's path, and refuses the upgrade otherwise. This is the container-ownership scope in action: a learner cannot craft a terminal connection to another learner's container, because the server derives both the identity and the ownership from trustworthy sources rather than from anything the client controls. Only once both checks pass does the server allocate the pseudo-terminal and run the shell.

The protocol across the WebSocket is deliberately small. Messages from the browser to the server are framed as JSON so that keystrokes and terminal-resize events can be distinguished: one message shape carries the bytes the learner typed, another carries the new column-and-row dimensions when the terminal is resized, and the server routes each to the pseudo-terminal accordingly. Messages from the server to the browser are the raw bytes the shell produced, written directly into the emulator. Because a real pseudo-terminal sits in the middle, the shell runs in fully interactive mode: tab-completion completes filenames and commands, the history is navigable with the arrow keys, line editing works, and an interrupt sent from the browser reaches the shell as a genuine interrupt. This was a deliberate upgrade over an earlier, simpler implementation that ran the shell without a pseudo-terminal and reconstructed line editing on the client; that earlier approach could not offer tab-completion or history because those are functions of an interactive shell attached to a terminal, and moving to a real pseudo-terminal on the server is what unlocked them. The cost of the upgrade was a native dependency and a corresponding adjustment to how the container image is built, which the report's operations part describes.

The terminal is also resilient to the ordinary turbulence of a live connection. If the WebSocket drops unexpectedly while the learner is still present, the client attempts to reconnect rather than stranding the learner at a dead prompt, and it distinguishes an unexpected drop from a deliberate departure so that leaving the lab does not trigger a pointless reconnection. This resilience also smooths over a development-mode quirk in which the workspace briefly mounts, unmounts and remounts, which would otherwise flash a spurious "session closed" message; with reconnection in place, the terminal simply re-establishes itself. Finally, the terminal participates in the platform's pedagogy: as the shell's output streams past, the client watches for the appearance of a flag and for other tell-tale patterns, and emits internal signals that the guided-missions system uses to tick off objectives automatically, so that a learner who reads the flag through the terminal sees the corresponding mission complete itself without having to claim credit manually.

## Chapter 13. The AI Mentor, "Sathi"

The platform includes an AI mentor, named Sathi — a Hindi word for companion — whose role is carefully bounded. It is not there to solve the exercises for the learner; it is there to give hints, to explain concepts, and to analyse what the learner has tried, in the manner of a patient teaching assistant who nudges rather than hands over the answer. This boundary is a pedagogical choice as much as a technical one, and it is reflected in the way the mentor is prompted and in the way its interface is structured around asking for a hint, an explanation or an analysis rather than around asking for the solution.

The mentor is designed to be provider-swappable through a single piece of configuration, and this is one of the clearest expressions of the platform's offline-first bias. If an external model provider is configured with an API key, the mentor uses it. If none is configured, the mentor automatically falls back to a local model served alongside the rest of the stack — a small, quantised model chosen specifically so that it runs within the memory budget of the target machine and requires no external connectivity whatsoever. The consequence is that the mentor works on an air-gapped deployment out of the box, degrading in capability rather than in availability when there is no external provider, which is exactly the right failure mode for an institutional platform that may be deployed in environments without reliable internet access. The health endpoint reports which provider is currently active, so an operator can see at a glance whether the mentor is running against the external provider or the local fallback.

Two further properties define the mentor's behaviour. The first is that it is economical with the model, because on a constrained machine the model is a scarce resource: requests are serialised through a shared, queued semaphore so that the mentor never tries to run several generations at once and exhaust memory, and many common questions are answered from pre-authored bilingual responses keyed to the specific beats of a lab, so that the model is invoked only for genuinely free-form questions rather than for every interaction. The second is that the mentor is hardened against prompt injection, which matters acutely in a platform whose subject includes prompt injection and whose learners are actively encouraged to think about how to subvert systems. The mentor treats the lab context and the learner's question as data to be reasoned about, not as instructions to be obeyed, so that a learner cannot talk the mentor out of its role or extract content it should not reveal by embedding instructions in their question. That the platform both teaches prompt injection as a vulnerability and defends its own mentor against it is another instance of the self-consistency that runs through the system.

## Chapter 14. The Module System and Content Manifests

Everything a learner sees in a laboratory — its title and summary, its lessons, its interactive widget or its scenario graph, its quiz, its guided missions, its enrichment material — is described by a single content manifest, and the manifest is the true centre of gravity of the platform's content architecture. The founding rule of the content system is that adding a laboratory is, in the ordinary case, a matter of writing a validated manifest rather than writing code. This rule keeps the content and the engine separate: the engine knows how to render a manifest of a given shape, and the manifest supplies the particular content, so that the catalogue can grow without the codebase growing in step.

The manifest is a single unified shape that accommodates both curricula, which is a deliberate economy. Common to every manifest are an identifier, a module classification of either application-security or awareness, an execution tier, a category, and the bilingual title and summary that appear on the catalogue card. From there the shape diverges according to the module. An application-security manifest carries a lifecycle of lesson sections — content passages, learning objectives, code comparisons of an insecure against a secure implementation, and the interactive section that names which exploit widget or live terminal the lab uses — together with its quiz, its guided missions, and its enrichment fields describing real-world impact, common mistakes, best practices and a mitigation checklist. An awareness manifest instead carries a scenario graph: a named start node and a map of nodes, each of which is a narration that sets a scene, a decision that offers choices, a consequence that shows the result of a choice, a feedback panel, or a checklist, with channels that tell the interface whether a given beat is an SMS, a chat, a video call, a payment request or an email, and with red flags attached to the beats where a tell-tale sign of the scam is visible. One envelope, two very different interiors, rendered by two different engines but managed by one system.

The manifest system was extended during development so that manifests need not only live as files on disk but may also be authored inside the application and stored in the database, and this extension was done with great care to preserve the uniformity that makes the rest of the system simple. Built-in laboratories remain files on disk, validated at boot. Administrator-authored laboratories live as complete manifests in the database and are folded into the same in-memory cache at startup and whenever they change, so that the code that serves a manifest, that mentors against it, or that spawns its container cannot tell the difference between a built-in and an authored lab. A settings overlay, keyed by identifier, lets an administrator enable, disable or reorder any laboratory regardless of its origin, so that a built-in lab can be hidden without editing a file and an authored lab can be promoted in the ordering. The learner-facing catalogue reflects this overlay, showing only enabled laboratories in the administrator-defined order, while the administrator's view shows everything with its provenance and its enabled state visible. This is the machinery that turns the platform from a fixed set of thirty-eight laboratories into an extensible system that an institute can grow on its own, and the front-end authoring tools that sit atop it are described in their own chapter.

# Part IV — The Learning Content

## Chapter 15. The Application-Security Laboratories

The application-security curriculum comprises twenty-two laboratories, and they are best understood not as a flat list but as a set of families, each family teaching a related failure of trust. What follows walks through those families in turn, describing what each laboratory places in front of the learner, what the learner does, and why the exercise is constructed the way it is. Throughout, it is worth remembering the tiered model: most of these labs are tier two, running a real vulnerable behaviour against the learner's own partitioned data; a handful are tier three, giving a real shell in a hardened container; one is a tier-one simulation; and four are tier-zero content labs that teach a discipline rather than an exploit.

The injection family is the oldest and most consequential in web security, and the platform gives it pride of place. The SQL-injection laboratory presents a login form whose query is built by concatenating the learner's input directly into the SQL string. The learner is invited first to bypass authentication with a boolean tautology — the classic apostrophe followed by an always-true condition — and to watch the login succeed without a valid password, and then to escalate to a union-based injection that appends columns from the accounts table so that secrets belonging to other seeded personas spill into the result. Every part of this is genuinely happening: the query really is being subverted, the rows really are being exfiltrated. What makes it safe is that the accounts the learner attacks are their own seeded rows, partitioned by owner, so that the tautology can never cross the tenancy boundary into another real learner's data. A reset restores the learner's sandbox. The lab then closes the loop pedagogically by showing the root cause — that the driver was never told which part of the query was data and which was code — and the secure fix, which is the parameterised statement that binds values as data so that no amount of quoting can change the query's structure. The command-injection laboratory is the injection family's tier-three member: it hands the learner a shell in a hardened container running a small "ping" helper that interpolates its argument into a shell command, and the learner appends a second command with a shell metacharacter to achieve arbitrary code execution, reads a flag that proves it, and then confirms that the sandbox holds by attempting to reach the internet and watching it fail because the container has no network at all. The same lesson — never build a shell command or a query from untrusted input — is taught twice, once against a database and once against a shell, which reinforces the general principle underneath the two specific instances.

The access-control family addresses the failures that dominate modern breach reports, in which the vulnerability is not exotic at all but simply a forgotten ownership check. The insecure-direct-object-reference laboratory presents an endpoint that fetches an invoice by its identifier without checking that the invoice belongs to the caller; the learner increments the identifier and reads invoices belonging to other personas, seeing plainly how a missing check turns a private resource into a public one. The broken-object-level-authorization laboratory raises the same failure to the level of an API and to write operations as well as reads: an order API returns and cancels orders by identifier without confirming ownership, and the learner reads another persona's order and then cancels it, experiencing the difference between an information-disclosure access-control failure and a state-changing one. Both labs are partitioned by owner in exactly the way the SQL-injection lab is, so that the direct-object-reference the learner performs reaches only their own seeded personas rather than any real learner's data; the vulnerability is real and the exploitation is real, but the blast radius is confined to the attacker.

The browser-trust family teaches the two canonical ways that the trust between a browser, a user and a site can be turned against them. The stored-cross-site-scripting laboratory presents a guestbook that stores comments exactly as submitted and later renders them without escaping, so that a comment containing a script executes in the context of whoever views it. Because executing arbitrary script in the context of the real single-page application would be genuinely dangerous, the lab renders the vulnerable guestbook inside a sandboxed frame, so that the learner's payload executes in a contained document rather than against the platform itself — the exploit is real, but its stage is isolated. The cross-site-request-forgery laboratory presents a profile-update endpoint that changes the account email with no anti-forgery token, and the learner constructs a forged request that performs the change as if the victim had willed it, learning why a state-changing endpoint must prove that the request came from the site's own forms rather than from an attacker's page. The authentication and session laboratories round out the trust family from a different angle: the broken-authentication lab presents a login that both reveals which usernames exist and imposes no lockout, so that a learner enumerates a valid user and then brute-forces a weak numeric PIN, while the session lab presents a forgeable session token encoded in a way the learner can decode and reconstruct, teaching why session tokens must be opaque and unguessable rather than a thin encoding of predictable data.

The server-side-request family and the parsing family are the tier-three heart of the advanced curriculum. The server-side-request-forgery laboratory teaches how an endpoint that fetches a URL on the server's behalf can be pointed at internal resources the attacker could not otherwise reach; because the tier-three container has no network, the lab teaches the shape and danger of the attack in a sealed environment where the danger cannot actually be realised against anything real. The XML-external-entity laboratory teaches how a parser configured to resolve external entities can be induced to read local files and disclose them, with the learner declaring an entity that points at a file on the container and watching its contents appear in the output. The insecure-deserialization laboratory teaches how reconstructing an object from an untrusted byte stream can be turned into code execution when the deserialiser is willing to instantiate arbitrary types. The path-traversal laboratory teaches how a file-serving endpoint that fails to canonicalise and confine its input can be walked up and out of its intended directory to read files elsewhere on the filesystem. Each of these lives in a hardened container precisely because each is most convincingly taught by letting the learner actually do it against a real, if minimal, system, and each is safe because that system is nearly inert, network-isolated and destroyed on exit.

The remaining hands-on laboratories address failures that are less about a single injectable point and more about the logic of the application. The business-logic laboratory presents a checkout that trusts the quantity and the coupons the client supplies and never enforces the rules that should govern them, so that the learner uses a negative quantity or stacks coupons to make the store pay them, learning that a vulnerability need not be a technical flaw in parsing but can be a gap in the rules the application forgot to enforce. The race-condition laboratory presents a wallet whose withdrawal is not atomic, so that the learner issues concurrent withdrawals that each see the same balance and together withdraw more than exists — the time-of-check-to-time-of-use flaw made tangible. The file-upload laboratory presents an upload that trusts the client's declared content type and permits a double extension, so that the learner smuggles a file past the check by spoofing its type or its name. The API-security laboratory presents a profile API that over-exposes internal fields on read and blindly accepts any field on update, so that the learner both reads fields they should not see and escalates their own privileges by assigning themselves an administrative flag through mass assignment. The language-model-security laboratory presents a hardened assistant and invites the learner to attempt prompt injection against it, teaching the newest member of the vulnerability catalogue through a deterministic simulation that models the attack without requiring a live model for the exercise itself. And the cloud-security laboratory, the platform's single tier-one simulation, presents a deterministic mock of a cloud command line in which a storage bucket is public and an access policy is over-permissive, teaching the shape of the most common cloud misconfigurations without any real cloud account being involved.

Finally, four laboratories teach disciplines rather than exploits, and they are tier zero because they are properly taught through structured content, guided reasoning and assessment rather than through a console. The secure-code-review laboratory teaches how to read code adversarially and spot the patterns that indicate a vulnerability. The threat-modelling laboratory teaches how to reason systematically about what could go wrong with a system before it is built. The incident-response laboratory teaches the disciplined sequence of steps that turns a security incident from a catastrophe into a managed event. The reconnaissance laboratory teaches passive information-gathering, the first phase of any assessment. These labs matter because a security professional who can only exploit but cannot review, model, respond or reconnoitre is only half-formed, and the curriculum is deliberately built to produce the whole practitioner rather than only the exploiter.

## Chapter 16. The Cyber-Awareness Laboratories and the Scenario Engine

The awareness curriculum is a different kind of teaching, and it is delivered by a different engine. Where an application-security lab is a lesson wrapped around an interactive exploit, an awareness lab is a branching story rendered inside a realistic phone simulation, and its purpose is not to impart a technique but to rehearse a decision. The sixteen awareness laboratories are all tier zero in the sense that they require no execution environment, but they are among the most sophisticated content in the platform, because a convincing scam is a subtle thing to reconstruct, and the engine that renders them is built to make the reconstruction convincing.

The scenario engine treats each awareness lab as a directed graph of nodes. A narration node sets a scene: the phone buzzes, an SMS arrives, a video call comes in, a payment request appears. A decision node stops the story and asks the learner what they would do, offering two or more choices, each of which leads to a different node — this is the heart of the exercise, the moment where a real victim chooses wrongly and where the learner is forced to choose at all. A consequence node shows the result of a choice: the trap path shows the money gone and the manipulation named, while the safe path shows the danger averted and the correct instinct affirmed. A feedback or checklist node distils the lesson into a short set of takeaways. Woven through the nodes are channels — the engine knows whether a given beat is an SMS, a WhatsApp chat, a video call, a payment request or an email, and renders it accordingly — and red flags, which mark the specific, observable tell-tale signs of the scam so that the learner learns not merely that something was wrong but exactly what they could have noticed. Every line of every node exists in both English and Hindi, so that the story reads naturally in whichever language the learner thinks in.

The subject matter is drawn directly from the fraud that Indian citizens face, and each lab reconstructs a specific manipulation. The digital-arrest laboratory reconstructs the scam in which a threatening SMS about a supposedly compromised Aadhaar-linked number leads to a video call from a man in a police uniform, sitting before a government logo, who invokes a fabricated money-laundering case and pressures the victim to transfer a "verification" sum that will supposedly be refunded; the safe path is to recognise that no real law-enforcement agency conducts arrests over video calls or demands transfers, to hang up, and to call the national cyber-crime helpline. The UPI-fraud laboratory reconstructs the collect-request trick in which a scammer posing as a buyer sends a payment request that, if approved, debits rather than credits the victim, teaching the counter-intuitive truth that one never approves a request or enters a PIN to receive money. The banking-fraud laboratory reconstructs the fake "card blocked" call that harvests an OTP. The KYC-scam laboratory reconstructs the fake update demand. The SIM-swap-and-OTP laboratory reconstructs the theft of a number and the sharing of a one-time password. The courier-and-customs laboratory reconstructs the parcel scam in which a caller claims an illegal package in the victim's name and threatens arrest unless a customs fee is paid. The fake-customer-care laboratory reconstructs the danger of searching for a support number and reaching a scammer who talks the victim into installing a remote-access application. The fake-job-offer laboratory reconstructs the task scam. The deepfake laboratory reconstructs the AI voice-clone of a relative in distress. The QR-scam laboratory reconstructs the payment-QR deception. The phishing laboratory reconstructs the look-alike domain and the urgent login link across email, SMS and WhatsApp. The social-media-safety laboratory reconstructs impersonation and romance scams. And the foundational laboratories — password security and multi-factor authentication, mobile security against malicious application packages, digital privacy around permissions and public Wi-Fi, and cyber hygiene around updates, backups and reporting — teach the habits that make all of the specific scams harder to land.

The pedagogical power of this format is that it rehearses the decision under something resembling the real conditions. A learner who has sat inside the digital-arrest scenario, felt the manufactured urgency, chosen to stay on the call, and watched the consequence unfold, has rehearsed the exact moment at which real victims fail, and has done so safely, with the manipulation named and the correct action shown. The red flags give them a concrete checklist of things to notice; the branching gives them the experience of the wrong choice without its cost; and the bilingual delivery ensures the lesson lands in the language of the people most at risk. It is worth noting that this same scenario data is what makes the platform's planned realistic-video production possible: because each narration and consequence node already specifies what the victim sees and on which channel, the nodes double as a shot list for producing short, phone-framed video clips that can play inside the mockup while the engine supplies the narration, choices and explanations around them — a separately-documented production specification derives directly from these manifests.

# Part V — The Front-End Application

## Chapter 17. The Web Application: React, Vite and the View Router

The entire user interface is a single-page application written in React and built by Vite, and its structure is deliberately lean. Rather than adopting a heavyweight routing library, the application organises itself around a small set of views — the dashboard, the two catalogues, the profile, the settings and support pages, and the administrative console — and switches between them with local state, opening a particular laboratory as a detail view layered over the catalogue. This view-based approach keeps the application's control flow legible and its dependency surface small, which is consistent with the platform's general preference for a few well-understood pieces over many powerful ones. At the top of the application sits the language context, which every piece of content consults to render itself in English or Hindi, and the authenticated-user state, which is loaded once at startup from the current-user endpoint and thereafter drives what the interface reveals.

The application's most important structural decision is how it loads the heavy machinery of the interactive laboratory. The immersive workspace, with its windowed desktop and its terminal emulator, is by far the largest single piece of the front-end, and the great majority of learners at any moment are reading a lesson or browsing the catalogue rather than sitting inside a live lab. It would therefore be wasteful to make every learner download the workspace and the terminal emulator on their first visit. The application instead loads the workspace lazily, as a separate bundle fetched only when a learner actually enters a laboratory's practice mode, so that the initial download contains only what is needed to read and navigate. This single decision more than halved the initial bundle, moving the terminal emulator and the whole windowed desktop into a chunk that a lesson-reader never fetches, and it is the kind of optimisation the five-gigabyte, modest-bandwidth deployment context rewards.

The application communicates with the lab manager through a thin, typed client that wraps every endpoint the interface needs, so that the components speak in terms of intentions — log in, fetch the catalogue, submit a quiz, create a user, author a module — rather than in terms of URLs and request bodies. Every request is credentialed with the session cookie, and errors are surfaced as typed exceptions that the components can present sensibly. This client is the single seam between the front-end and the back-end, and keeping it thin and typed means that a change to the back-end surface is reflected in one place rather than scattered across the components.

## Chapter 18. The Design System, Branding and Bilingual Experience

The platform is a government product for a national institute, and its visual language was chosen to reflect that rather than to look like a generic software-as-a-service application. The interface carries the official emblem and the institute's branding, presents itself under the name of the training programme in both scripts, and uses a restrained, official palette. During development this palette was deliberately shifted from a bright, consumer blue to a deeper navy, and the interface's corner radii were reduced across the board, because the earlier styling read as slightly amateurish and the intent was a more mature, institutional look; these adjustments were made through the design tokens so that a single change to the token propagated everywhere the token was used, which is the payoff of having expressed the design as tokens in the first place.

The design system is expressed as a layer of tokens — colours, the accent, the surface and border treatments, the base radius — and a set of semantic component styles built upon them: the card, the button in its several variants, the input, the chip, the navigation item, the laboratory card, and so on. Because the components are styled through these semantic classes rather than through scattered inline decisions, the interface is consistent and adjustable, and the entire look can be tuned from the token layer. The typography pairs a Latin face with a Devanagari face so that Hindi is a first-class citizen of the type system rather than a fallback, and the interface is built to respond to both light and dark presentation and to the viewer's language preference, which it persists to the learner's profile so that their choice follows them across sessions.

The bilingual experience deserves its own emphasis because it is so pervasive. The language toggle in the header switches the entire interface instantly, without a reload, because every piece of content is a small object carrying both an English and a Hindi string and the rendering simply selects one according to the current language. This is why the platform reads as genuinely bilingual: there is no moment at which the Hindi runs out and English shows through, because the two languages are carried together at every leaf. For the awareness content in particular this is not a nicety but a necessity, since the citizens most exposed to the scams the platform teaches are frequently more comfortable in Hindi, and a scam scenario that lapsed into English at the crucial moment would fail exactly the audience it most needs to reach.

The laboratory cards illustrate the care taken with the interface's texture. Each of the thirty-eight laboratories carries a distinct, on-theme icon rather than a generic one — a database for the injection labs, a fingerprint for authentication, a gavel for the digital-arrest scam, a rupee for UPI fraud, a mail-warning for phishing — and each icon sits inside a rounded tile with a per-topic gradient and a subtle sense of depth, so that the catalogue reads as a set of distinct, considered products rather than a list of interchangeable rows. These tiles are rendered entirely from vector glyphs and CSS gradients, with no external image assets and no network requests, which keeps them consistent with the platform's offline-first posture: the catalogue looks rich but downloads nothing to achieve it.

## Chapter 19. The Immersive Lab Workspace

When a learner chooses to practise rather than merely to read, the platform presents an immersive workspace that is one of its most distinctive pieces of interface. The lesson gives way to a full-screen, windowed desktop — a small operating-system-like environment with draggable, focusable windows, a taskbar, and a dark, glassmorphic aesthetic — inside which the actual exercise takes place. For a tier-two laboratory, one of the windows holds the exploit console for that lab; for a tier-three laboratory, one of the windows holds the live terminal into the container. Alongside it sits a missions window that tracks the learner's objectives. The effect is to move the learner from the posture of reading about a technique to the posture of operating a tool, which is a meaningful psychological shift for a practical exercise, and it is deliberately reminiscent of the working environment a security professional actually inhabits without importing the weight or the risk of a full offensive-security desktop.

The workspace is built from a small window-management system implemented with React's own state primitives rather than an external dependency, expressing the windows, their stacking order, their focus, and their minimised or maximised state as reducer-managed state. Draggable windows, the taskbar, and the window frame are each small, focused components composed together. The whole assembly is scoped so that its styling cannot leak into the rest of the application, and it is layered so that the global mentor remains reachable above it, because a learner in the middle of an exercise is exactly the learner most likely to want a hint. This care with layering and scoping is what lets the workspace be a dramatic, full-screen departure from the rest of the interface without destabilising it.

The workspace also owns the lifecycle of the tier-three container, and this is where its engineering is most careful. On entering a container lab it starts the container and begins sending the heartbeats that keep the slot alive; on leaving it stops the container so that the box is reaped promptly rather than waiting for the idle timeout. The subtlety, described earlier and revisited in the history chapter, is that the naive version of this lifecycle could race against itself under a development-mode behaviour that mounts, unmounts and remounts the workspace in quick succession, because the start and stop calls were fire-and-forget and could arrive at the server out of order, leaving an orphaned container. The workspace was therefore reworked to start the container exactly once per session and to defer the stop until the start had definitely completed, which made the lifecycle correct under the churn as well as in the ordinary case. It is a small piece of code with a disproportionate amount of reasoning behind it, which is characteristic of the parts of the system that touch real infrastructure.

## Chapter 20. Guided Missions and Automatic Detection

A practical exercise is more instructive when the learner has a clear sequence of objectives, and the platform provides these through a guided-missions system that sits beside the exercise in the workspace. Each laboratory can declare a short list of missions — understand the query, bypass the login, exfiltrate the secret, state the fix — and the missions window presents them as a checklist with a progress indicator. The distinguishing feature of the system, and the reason it is more than a static list, is that most missions tick themselves off automatically when the learner actually does the thing, rather than requiring the learner to claim credit.

The automatic detection works through a small internal signalling mechanism. As the learner operates the exercise, the interactive widgets and the terminal emit signals describing what just happened: the exploit console for the SQL-injection lab emits a signal when a genuine authentication bypass occurs and another when a flag appears in the exfiltrated rows, and the terminal watches the shell's output stream for patterns — a flag, an identity string that proves a command ran, a network error that proves the sandbox held — and emits signals accordingly. The missions system listens for these signals and, for any mission whose declared trigger matches, ticks it off. Missions that correspond to something the learner can genuinely do are therefore self-verifying, and only the reflective missions — those that ask the learner to articulate a fix — retain a manual acknowledgement, because there is nothing to detect for a mission whose completion is a thought rather than an action. The design intent, stated in the interface itself, is that the learner should complete the objectives by doing the work rather than by reading the answer, and the automatic detection is what makes that intent enforceable without being oppressive: the missions reward action and are indifferent to claims.

For the command-injection laboratory, this system was tuned with particular care, because the detection had to be precise enough not to fire spuriously. Running the identity command genuinely ticks the reconnaissance objective because its output contains an unmistakable pattern; injecting a second command through the vulnerable helper ticks the injection objective because the injected command's output appears after the ping statistics in a way that ordinary use does not produce; reading the flag ticks the exfiltration objective; and attempting to reach the internet ticks the sandbox-confirmation objective precisely because the attempt fails with a network-unreachable error that only appears when egress is attempted against a network-isolated container. Each detection was chosen to match the genuine evidence of the intended action rather than a proxy for it, so that the missions are honest reflections of what the learner accomplished.

## Chapter 21. The Admin Console and In-Application Authoring

The administrative console is the platform's answer to the reality that an institute will want to run the system itself — to enrol its own learners, to organise them into the batches it actually teaches, and, over time, to add training content of its own — without a developer's involvement. The console is revealed only to users who hold the administrative permissions, and it is organised into three areas that correspond to the three things an administrator manages: the learners, the batches, and the modules.

The learner-management area lets an administrator provision an account by supplying an email, a display name, a temporary password and a role, and it presents the roster of existing accounts with their roles, their batch memberships and their status. Its most considered feature is the account lifecycle, which the platform deliberately made a two-step affair. When an administrator removes a learner, the account is first deactivated: it is suspended, it can no longer log in, but its records — its progress, its scores, its certificates — are retained, and its deactivation is reversible. Only once an account is deactivated may it be deleted permanently, at which point its data is cascaded away. This deactivate-then-delete sequence was a specific choice made in consultation with the requirement, and the back-end enforces it: an attempt to delete an account that is still active is refused with an explanatory error, so that the destructive step cannot be taken by accident. Granting a role beyond the ordinary learner role additionally requires the role-assignment permission, so that the power to create administrators is held separately from the power to create accounts, and every one of these operations is written to the audit log.

The batch-management area operationalises the cohort model that the data layer provides. An administrator creates a batch, adds learners and instructors to it, removes members, and — the requirement that motivated the batch status column — suspends a batch once its course is complete, reversibly, or deletes it outright. The interface presents each batch with its status, its membership and the controls to manage it, and the underlying operations are all permission-gated and audited in the same way as the learner operations. This area is what turns the abstract cohort tables into a usable tool for an instructor-led institution, and it is what gives the instructor role its meaning, because a batch is precisely the scope over which an instructor is entitled to see.

The module-management area is the most ambitious, because it exposes the content system itself to the administrator. It lists every laboratory, built-in and authored alike, with its module classification, its tier, its provenance and its enabled state, and it lets the administrator enable or disable any laboratory and, for authored laboratories, edit or delete them. Behind a single button sits the in-application authoring tool, which is a genuine form-based editor for a complete content manifest. For an application-security module it offers the metadata fields, a repeatable editor for the lesson sections in each of their varieties, a quiz editor in which each question's choices are entered and the correct one is marked, and a missions editor. For an awareness module it offers instead a scenario-node editor, in which nodes are created, typed, given their bilingual content, and — for decision nodes — given their choices and the nodes those choices lead to, with a start node selected from among them. Every text field is bilingual, presenting an English and a Hindi input side by side, so that an authored module is bilingual by construction rather than as an afterthought.

The authoring tool's handling of quiz answers is the detail that best shows the care taken to preserve the platform's invariants. The editor lets the administrator mark the correct choice for each question, because an author obviously needs to specify the answer; but when the module is saved, the server extracts those correct-answer markings, writes them into the server-side key table, and stores and serves a manifest with the markings removed, so that a learner who fetches an authored laboratory receives exactly the same key-free content as they would for a built-in one, and the authoritative-grading property is preserved without the author having to think about it. When the administrator reopens the module to edit it, the server re-attaches the keys for their eyes only. In this way the authoring tool grants full creative control over new content while quietly maintaining the security and integrity properties that the rest of the platform depends upon, and an institute can grow its own curriculum without ever being able to accidentally leak an answer key to a learner.

## Chapter 22. Profile, Settings and Support

The learner-facing account surfaces are modest by design, but they were completed rather than left as stubs, because a platform that presents dead navigation entries reads as unfinished. The profile page shows the learner their identity, their roles and their certificates, and lets them edit their display name; a change is written through the self-service endpoint and reflected immediately in the header, so that the learner sees their own edit take effect. The settings page gathers the account controls that belong together: the language preference, which is persisted to the profile so that it follows the learner across sessions and devices; the password change, which requires the current password and confirms the new one before submitting it; and a read-only summary of the account's email and roles. Both pages are careful to update the application's view of the current user when something changes, so that the interface never drifts out of step with the server.

The support page was built from the real contact details of the NIELIT Haridwar centre and presents them as a usable directory rather than a block of text: the centre's postal address with a link to a map, its office hours, its telephone, mobile and messaging numbers as click-to-call and click-to-message links, a directory of departmental email addresses each as a click-to-compose link, and links to the centre's social presence rendered with the official brand marks of the respective platforms. The social marks and the messaging logo are inlined as vector paths rather than fetched from a content-delivery network, which keeps the support page consistent with the platform's offline-first posture — the page looks like a polished contact card and yet makes no external request to render itself, so it works on an air-gapped deployment exactly as it does on a connected one. The page's headings follow the language toggle like the rest of the interface, so that a Hindi-preferring user reads their support directory in Hindi.

# Part VI — Operations, Security and Quality

## Chapter 23. Containerisation and Deployment

The platform is delivered as a set of containers orchestrated by Docker Compose, and the composition is arranged so that the whole system stands up with a single command and fits within the target machine's memory. The database and the Redis instance run from official Alpine-based images with explicit memory limits. The lab manager runs from an image built in two stages so that its native terminal dependency is compiled once, against the runtime's Node version, in a build stage that carries the necessary compiler toolchain, and then only the compiled result and the production dependencies are carried into a slim runtime image that adds just the small runtime library the native addon needs and the Docker command-line client the container lifecycle requires. This two-stage arrangement keeps the runtime image small while still allowing the native addon to be built correctly, and it was the specific consequence of moving the terminal to a real pseudo-terminal, because a pseudo-terminal requires a native addon and a native addon requires a compiler at build time but not at run time.

The lab manager container is given access to the host's Docker socket, which is what allows it to spawn the tier-three target containers as siblings on the host rather than as nested containers. This is a powerful grant and it is made deliberately and with awareness of its weight, because sibling containers are both more efficient and, run under the hardened configuration and the stronger sandbox runtime, more defensible than the nested alternative. The manifests directory is mounted into the lab manager read-only, so that the built-in content can be updated without rebuilding the image, while the authored content lives in the database and needs no mount. The database's schema and seed are applied at initialisation, and subsequent structural changes are applied as idempotent migrations against the running database, because the initialisation scripts run only against an empty data volume and would not otherwise reach a database that already holds state.

One operational subtlety deserves recording because it shaped the build configuration. The native terminal addon must fetch the correct headers for the container's Node version when it compiles, and the build environment on the development machine had no outbound network access during the image build, which caused the compilation to fail. The build was therefore configured to run on the host network so that the compiler could reach the header source, and this configuration was folded into the compose build definition so that the image builds reproducibly. It is a small piece of operational knowledge, but it is exactly the sort of thing that a report of this kind exists to capture, because it is invisible in the running system and yet essential to reproducing it.

## Chapter 24. Security Posture and Threat Model

A platform whose subject is security is held, rightly, to a higher standard in its own construction, and the platform's posture reflects a consistent set of principles rather than a scattering of individual measures. The first principle is that identity is never trusted from the client. Every request derives its acting user from a signed session that the client cannot forge, and no privileged operation reads a user identifier from a header or a URL, which structurally removes the entire class of identity-tampering attacks. The second principle is deny-by-default authorization through a single gate. Every protected route passes through one middleware that checks a required permission and, where relevant, a scope, so that there is no route that forgot to check and no ad-hoc check to get subtly wrong; the powers of a role live in data, and cross-user access is both gated by scope and recorded in the audit log. The third principle is that outcomes are decided by the server. The browser sends actions and the server decides what they mean, so that scores and certificates reflect what a learner actually did rather than what they claimed, and quiz answer keys never leave the server at all.

The container hardening is the fourth pillar, and it is where the platform's threat model is most explicit, because tier three deliberately gives a learner code execution on the host machine and must contain the consequences. The threat is that a learner, having a shell, attempts to reach other learners' data, to reach the host or the internal network, to persist, or to exhaust the host. Each of these is answered directly: the network is disabled entirely so there is nowhere to exfiltrate to or pivot toward; the filesystem is read-only but for a small non-executable scratch space so nothing can be persisted or executed; every capability is dropped so the usual privilege-escalation primitives are unavailable; the memory and process counts are capped so the host cannot be exhausted; a stronger sandbox runtime is layered underneath in production so a kernel-level escape meets another barrier; and the container is destroyed on exit and reaped if abandoned so that nothing lingers. The container-ownership scope ensures a learner cannot even attach to another learner's container, and the global slot limit ensures the number of containers is bounded regardless of demand. The tier-two model answers the analogous threat for the shared vulnerable applications by partitioning every lab's data by owner, so that a genuinely-working exploit reaches only the attacker's own rows.

The remaining measures round out the posture. Passwords are hashed with a slow adaptive hash and never stored or logged in plaintext. Sessions are carried in signed, HTTP-only, same-site cookies, secured in production. The login endpoint is written not to reveal which accounts exist. The mentor is hardened against prompt injection so that it cannot be talked out of its role, which matters especially because the platform actively teaches prompt injection. Certificates are signed so they cannot be forged and can be verified without trusting the presenter. Every privileged write and cross-user read is audited. And the whole system is designed to run air-gapped, which is itself a security property, because a platform that needs no outbound connection presents a far smaller attack surface than one that reaches out to cloud services during ordinary operation. The self-consistency of all this is worth restating: a platform that teaches injection uses parameterised queries and visible SQL, a platform that teaches broken access control centralises its ownership checks, and a platform that teaches prompt injection defends its own model — the curriculum and the construction reinforce one another.

## Chapter 25. Performance and the Five-Gigabyte Budget

The memory budget is the constraint that disciplines the whole system, and the platform meets it not through any single trick but through a consistent refusal to spend resources it does not need to spend. The tiered execution model is the largest contributor: because most laboratories are content or simulation and consume almost nothing, and because even the tier-two labs share a single application partitioned by data rather than running a process per learner, the only genuinely heavy resource — a live container — is reserved for the handful of exercises that truly require it, capped in number by the global slot limit, and destroyed the moment it is no longer in use. A machine hosting this platform is therefore, at any moment, running a small back-end, two modest data stores, a static file server, an optional small language model, and only as many tier-three containers as are actively in use up to a fixed ceiling, each of those containers itself capped tightly in memory. The sum stays within the envelope by construction rather than by luck.

The front-end contributes its share of the discipline. The decision to load the immersive workspace lazily means that the initial download a learner receives contains only the interface needed to read and navigate, with the terminal emulator and the windowed desktop deferred into a separate chunk fetched only on entering a laboratory; this more than halved the initial script payload and removed the build tool's own warning that the bundle had grown too large. The dead code left behind by the workspace redesign was removed rather than left to bloat the bundle. Even the imagery is disciplined: the national emblem, a detailed vector, was optimised to roughly half its size without visible loss because it renders small, and the laboratory icons and social marks are drawn from vector glyphs and gradients rather than raster assets, so the interface looks rich while downloading almost nothing. None of these is dramatic on its own, but together they express the same posture as the back-end: spend only what the moment requires.

The AI mentor is where the budget shaped a capability directly. A large language model is out of the question on a five-gigabyte machine, so the offline mentor uses a small quantised model, and the mentor's design compensates for the model's modest capability by answering common questions from pre-authored responses and reserving the model for genuinely free-form questions, and by serialising requests through a queued semaphore so that concurrent demand never multiplies the model's memory cost. The result is a mentor that is present and useful on an air-gapped, constrained machine, which is a more valuable property in this deployment context than a more capable mentor that required a connection or a larger machine would be. Throughout, the platform makes the same trade in the same direction: it prefers a system that runs reliably within its means over one that would be more capable if only it had more.

## Chapter 26. A History of the Engineering Decisions

It is worth closing the technical narrative with an account of how the current state came to be, because the platform did not arrive fully formed and several of its most instructive properties are the residue of specific problems solved. The foundation was laid first: the tiered execution model, the deny-by-default authorization, the data model, and the two curricula were built and verified as a working whole, bilingual throughout and server-scored, running within the budget. The interface was then restyled to the governmental design language, adopting the official branding and rebuilding the awareness experience as a realistic phone simulation.

The application-security laboratories were then reconceived around an education-first structure. Where an earlier version presented an exercise more or less directly, the redesign split each laboratory into a lesson that leads with the real-world impact, the common mistakes, the best practices and a mitigation checklist, and a practice mode reached through a deliberate "go to lab" step that opens the immersive windowed workspace. This split was chosen so that the learner meets the concept before the console, and it was accompanied by the guided-missions system so that the practice has a clear shape. The workspace itself was adapted from an early prototype of a windowed desktop but rebuilt onto the platform's own foundations, with its window management expressed in the platform's own state primitives and its terminal wired to the platform's own container transport rather than the prototype's.

The terminal was then upgraded from a client-simulated line editor to a genuine pseudo-terminal on the server, which is what gave it tab-completion, history and true interactivity, at the cost of a native dependency and the corresponding two-stage container build. Alongside this, the guided missions were made self-verifying through the signalling mechanism, so that objectives tick themselves off when the learner genuinely performs the action rather than when they claim to. Several bugs of the instructive kind were found and fixed in this period: the container lifecycle was reworked to eliminate a race, between fire-and-forget start and stop calls under a development-mode remount, that could orphan a container the slot-based reaper would not catch, by starting the container exactly once per session and deferring the stop until the start had completed; the terminal was given a guarded reconnection so that a transient drop or the same development-mode churn would not strand the learner; and the login response was extended to carry the full user with roles and permissions, because the interface had come to depend on the permissions being present to decide whether to reveal the administrative area and would otherwise fail on a fresh login.

The platform was then made extensible and self-serviceable. The dead code left by the redesign was removed and the front-end was code-split and its assets optimised. The administrative console and the in-application authoring tools were built on top of the pre-existing but previously-unused permission catalogue and cohort tables, turning latent capacity in the data model into working features, with the account lifecycle made a deliberate deactivate-then-delete sequence and the authoring tool made to preserve the answer-key discipline automatically. The support page was completed from the institute's real contact details, the laboratory catalogue was given its distinct on-theme iconography, and the visual language was matured with a deeper palette and tighter geometry, along with a collapsible sidebar for the desktop. Most recently, the awareness scenario data was distilled into a video-production specification, so that the branching stories can be filmed as short, phone-framed clips that play inside the mockup while the engine supplies the narration and logic around them.

The through-line of this history is that the platform grew by consolidation as much as by addition. Several of its later features — the admin console, the batch management, the authoring — were not built on empty ground but on foundations laid at the very start, in the permission catalogue and the cohort tables that anticipated them. Several of its refinements were the disciplined removal of things rather than the addition of them. And several of its most careful pieces of code exist because a real piece of infrastructure — a container, a terminal, a session — behaved in a way that a naive implementation did not anticipate, and the fix left behind a small, well-reasoned piece of machinery. This is the ordinary texture of a system that is genuinely built rather than merely specified, and it is recorded here so that whoever inherits the platform understands not only what it does but why it is shaped the way it is.

## Appendix A. The Permission Catalogue

The platform's authorization vocabulary names both the permissions its current features exercise and the permissions it is designed to grow into. The learner-facing permissions govern access to laboratories, use of the mentor, submission of quizzes, and self-service reading of one's own scores, certificates and progress. The teaching permissions govern the assignment of learners to cohorts and the monitoring, review and reporting over those cohorts, and they are what the trainee and instructor roles carry. The content permissions govern editing modules, uploading datasets and managing localisation, and they are what the authoring tools exercise. The administrative permissions govern managing users, assigning roles, switching the model provider, issuing certificates and viewing the audit log. The four roles compose these permissions additively: the student holds the learner permissions; the trainee adds the cohort-monitoring permissions; the instructor adds the cohort-assignment and content permissions; and the administrator holds the full set. Because the grants are stored as data rather than expressed in code, this composition can be adjusted, and new roles introduced, without touching the application.

## Appendix B. The Complete Laboratory Inventory

The application-security curriculum comprises twenty-two laboratories. In the injection family are SQL injection and command injection. In the access-control family are the insecure direct object reference and broken object-level authorization. In the browser-trust family are stored cross-site scripting, cross-site request forgery, broken authentication and session management. In the advanced hands-on family are server-side request forgery, XML external entity injection, insecure deserialization and path traversal. In the logic-and-configuration family are business-logic flaws, race conditions, insecure file upload, API security, language-model security and cloud security. And in the disciplines family are secure code review, threat modelling, incident response and reconnaissance. By tier, four are pure content, one is a simulation, twelve run a shared vulnerable application partitioned per learner, and five run an ephemeral hardened container.

The cyber-awareness curriculum comprises sixteen laboratories, each a branching scenario: banking fraud built on a card-blocked call and OTP theft; the courier and customs parcel scam; cyber hygiene around updates, backups and reporting; deepfake and AI voice-clone scams; the fake-police "digital arrest" video call; digital privacy around permissions, location and public Wi-Fi; fake customer care paired with remote-access applications; the fake job offer and task scam; the KYC-update scam; mobile security against malicious application packages; OTP sharing and SIM swap; password security and multi-factor authentication; phishing across email, SMS and WhatsApp; the QR-code scam; social-media safety against impersonation and romance scams; and UPI payment fraud built on the collect request.

## Appendix C. The Awareness Video-Production Specification

The awareness scenario manifests double as a specification for producing realistic video that plays inside the phone mockup. Because each narration and consequence node already declares what the victim sees and on which channel, the nodes constitute a shot list: the beats that depict the phone screen become short clips, while the decision, feedback and checklist beats remain rendered by the application. Across the sixteen laboratories this yields roughly fifty short clips totalling on the order of eight to nine minutes of phone-screen footage, with the labs cleanly divided into those that are screen-only — phishing, QR, mobile security, password security, digital privacy and cyber hygiene — and those that require a recurring on-camera character, such as the police officer of the digital-arrest scenario or the fake buyer of the UPI-fraud scenario, for which a character reference and a consistent first frame keep the production uniform across clips. The specification is maintained separately as a per-node shot list with durations, channels and on-screen content derived directly from the manifests, so that it stays faithful to the scenarios it films.

## Appendix D. Glossary of Terms

*Tier.* The execution classification of a laboratory, from tier zero (pure content) through tier one (server-side simulation) and tier two (a shared vulnerable application partitioned per learner) to tier three (an ephemeral hardened container).

*Manifest.* The single content document that fully describes a laboratory — its metadata, its lessons or scenario graph, its quiz, its missions and its enrichment — and from which the appropriate engine renders it.

*Cohort.* A batch of learners, the scope boundary around which the instructor role revolves and which an administrator can form, populate, suspend and dissolve.

*Scope resolver.* A function that decides whether an actor's reach extends to a particular target — the self scope, the cohort scope and the container-ownership scope — and which, together with the permission gate, constitutes the platform's deny-by-default authorization.

*Reaper.* The interval process that destroys tier-three containers that have been idle beyond a threshold or alive beyond a maximum lifetime, freeing their slots and guaranteeing that the host never carries stale boxes.

*Mission.* A declared objective within a practical laboratory, most of which tick themselves off automatically when the learner performs the corresponding action, detected through an internal signalling mechanism.

*Sathi.* The platform's AI mentor, provider-swappable between an external model and a small local model, hardened against prompt injection, and designed to give hints rather than answers.

# Part VII — Technical Reference

This part turns from narrative to reference. It documents the concrete technical surfaces of the platform — the HTTP and WebSocket interfaces, the database tables and their columns, the wire protocols spoken across the network boundaries, the manifest schema that describes all content, and the step-by-step sequences that the most important operations follow. Where the earlier parts explained why the system is shaped as it is, this part records precisely what it exposes, so that an engineer inheriting the platform can navigate it without reading the source first.

## Chapter 27. The HTTP and WebSocket Interface

The lab manager exposes a single HTTP surface, mounted under a set of routers, together with one WebSocket endpoint for the terminal. Every route below the two public endpoints requires a valid session, and every administrative route additionally requires a specific permission, checked by the single authorization gate described in Chapter 8. What follows is a faithful account of that surface, grouped by router.

**Public endpoints, requiring no authentication.** The health endpoint, reached with a GET at `/health`, confirms that the database and Redis are reachable and reports which mentor provider is active; it is what an orchestrator's liveness probe consults. The certificate-verification endpoint, reached with a GET at `/verify/:certId`, takes a certificate identifier and returns the certificate's verified contents or a not-found response; it is deliberately unauthenticated so that anyone — an employer, an examining body — can confirm a certificate without an account.

**Authentication, under `/auth`.** A POST to `/auth/login` takes an email and a password and, on success, sets the session cookie and returns the full authenticated user including roles and permissions; it refuses a deactivated account with a distinct status. A POST to `/auth/logout` clears the session cookie. A GET to `/auth/me` returns the currently authenticated user, and is how the front-end rehydrates the session on load.

**Laboratories, under `/labs`.** A GET to `/labs` returns the learner-facing catalogue — the enabled laboratories, built-in and authored, in administrator-defined order, each reduced to the fields the catalogue card needs. A GET to `/labs/:id` returns the full manifest for one laboratory, safe to ship because answer keys never live in the manifest. The tier-three container lifecycle is driven by a POST to `/labs/:id/start`, which claims a slot and spawns or reuses the learner's container and reports the tier and status, a POST to `/labs/:id/heartbeat`, which keeps the slot alive, and a POST to `/labs/:id/stop`, which reaps the container and is ownership-scoped so a learner can only stop their own. Assessment is submitted with a POST to `/labs/:id/quiz`, which grades the submitted answers against the server-held key and returns the score and which questions were correct. The tier-two laboratories add their own endpoints — for example a POST to `/labs/sqli/login` runs the injectable query and reports whether an exploit was detected, a POST to `/labs/sqli/reset` restores the learner's sandbox, a GET to `/labs/idor/invoice/:id` performs the vulnerable fetch, and a GET to `/labs/bola/order/:id` with a companion cancel endpoint performs the object-level-authorization exercise — each of which operates only against the learner's own owner-partitioned data. Finally, the terminal WebSocket is reached by upgrading a connection at `/labs/:id/terminal`, authenticated from the session cookie and authorized by container ownership.

**Self-service, under `/me`.** A GET to `/me/scores/:labId` returns the learner's own score for a lab, a GET to `/me/certificates/:labId` returns their certificate if earned, and a GET to `/me/progress` returns their progress across labs. A PATCH to `/me/profile` updates the learner's own display name and locale, and a POST to `/me/password` changes their password after verifying the current one. Every endpoint here is scoped to the session identity, so there is no user identifier in any of these URLs for anyone to tamper with.

**Mentor, under `/mentor`.** A POST to `/mentor/ask` takes a lab context, a question and a locale, and streams the mentor's answer back as a token stream over server-sent events. A GET to `/mentor/provider` reports which provider is active.

**Administration, under `/admin`.** User management is a GET to `/admin/users` for the roster, a POST to create an account, a PATCH to `/admin/users/:id` to update its name, locale or roles, POSTs to `/admin/users/:id/deactivate` and `/reactivate` for the reversible suspension, and a DELETE to `/admin/users/:id` for the permanent deletion that is only permitted once an account is deactivated. Batch management is a GET to `/admin/cohorts` for the batches with their members, a POST to create one, a POST to `/admin/cohorts/:id/members` to add a member and a DELETE to `/admin/cohorts/:id/members/:userId` to remove one, POSTs to `/admin/cohorts/:id/suspend` and `/reactivate`, and a DELETE to remove the batch. Module management is a GET to `/admin/modules` for the full catalogue with provenance, a GET to `/admin/modules/:id` that returns the editable manifest with answer keys re-attached for the author's eyes, a POST to create an authored module, a PUT to `/admin/modules/:id` to update one, a PATCH to `/admin/modules/:id/settings` to enable, disable or reorder any module, and a DELETE to remove an authored one. A GET to `/admin/roles` lists the role names for the account-creation form. Every write in this router is permission-gated and written to the audit log.

## Chapter 28. The Data Dictionary

This chapter documents every table in the durable store, its columns and its purpose, so that the schema can be understood without reading it. The identity and access-control tables come first, then the learning machinery, then the per-laboratory data.

The **users** table holds one row per account: a universally-unique identifier as primary key, a unique email, a bcrypt password hash, a display name, a preferred locale, a status of active or deactivated with the timestamp of deactivation, and a creation timestamp. The **roles** table names the roles with a serial identifier and a unique name. The **permissions** table names the permissions likewise. The **role_permissions** table joins roles to the permissions they grant, keyed by the pair. The **user_roles** table joins users to the roles they hold, keyed by the pair. Together these five tables implement the additive role-based access control described in Chapter 8, with a user's effective permissions computed as the union across their roles.

The **cohorts** table holds one row per batch: an identifier, a name, a status of active or suspended with a suspension timestamp, and a creation timestamp. The **cohort_members** table joins users to cohorts with a role of learner or instructor, keyed by the cohort-and-user pair, and is the raw material for the instructor's cohort scope.

The **events** table is the telemetry spine, one row per meaningful moment: a big-serial identifier, the acting user, the lab, an event type drawn from a fixed vocabulary — lab started, exploit attempted, exploit succeeded, decision made, quiz answered, node completed, lab completed, hint requested — an optional node identifier, an outcome classification, a JSON payload, and a timestamp, with an index on user-and-lab for efficient per-learner queries. The **quiz_keys** table holds the correct answers, keyed by lab-and-question, each with the correct choice or choices as JSON and a point value; it never leaves the server. The **scores** table holds a learner's score and maximum score per lab, keyed by user-and-lab, with an update timestamp. The **progress** table holds a completion flag and a JSON state blob per learner per lab, keyed by user-and-lab. The **certificates** table holds one row per earned certificate: an identifier, the user, the lab, the score, the signature over the canonical payload, and an issue timestamp, with a uniqueness constraint on user-and-lab that makes issuance idempotent. The **audit_log** table holds one row per privileged write or cross-user read: a big-serial identifier, the actor, the action, an optional target, a JSON detail, and a timestamp.

The content-authoring tables are two. The **modules** table holds administrator-authored laboratories: an identifier as primary key, the module classification, the full manifest as a JSON document, the authoring user, and creation and update timestamps. The **module_settings** table holds the visibility-and-ordering overlay keyed by module identifier, with an enabled flag and a sort order, applying uniformly to built-in and authored modules.

The per-laboratory tables each carry an owner identifier that is the tenancy boundary. The **lab_sqli_accounts** table holds each learner's seeded accounts for the SQL-injection lab, with a username, a deliberately-plaintext password that is the secret to exfiltrate, a role, and a secret note, keyed by owner-and-username. The **lab_idor_invoices** table holds each learner's personas' invoices for the direct-object-reference lab, with an invoice identifier, the owning persona, an amount and a secret, keyed by owner-and-invoice. The **lab_xss_comments** table holds each learner's guestbook comments stored raw for the stored-cross-site-scripting lab, with an author and a body, indexed by owner. The **lab_csrf_profile** table holds each learner's profile email for the cross-site-request-forgery lab. The **lab_auth_accounts** table holds each learner's weak-PIN victim account for the broken-authentication lab. The **lab_bola_orders** table holds each learner's personas' API orders for the object-level-authorization lab, with an item, a status and a secret. The **lab_race_wallet** table holds each learner's wallet balance for the race-condition lab. The **lab_api_profile** table holds each learner's over-exposed, mass-assignable profile for the API-security lab, including the fields — a role, an administrative flag, an internal note — that the vulnerability improperly discloses or allows to be set. In every case the owner identifier confines the deliberately-vulnerable behaviour to the attacking learner's own rows.

## Chapter 29. The Wire Protocols

Three protocols cross the network boundary between the browser and the lab manager beyond ordinary request-and-response JSON, and each is documented here.

The **terminal protocol** runs over the WebSocket at the terminal endpoint. From the browser to the server, messages are JSON-framed so that two kinds of client intent can be distinguished: an input frame carries the bytes the learner typed as a string, and a resize frame carries the new column-and-row dimensions as a pair, which the server applies to the pseudo-terminal so that the shell's own formatting matches the emulator's size. From the server to the browser, messages are the raw bytes the shell produced, written directly into the emulator without framing, because the emulator's job is simply to render them. The asymmetry is deliberate — the client must tell the server which of two things it means, but the server need only stream output — and it keeps the server-to-client direction as fast and simple as possible.

The **mentor protocol** runs over server-sent events on the mentor endpoint. The request is an ordinary POST carrying the lab context, the question and the locale. The response is a stream of events, each a data line carrying a small JSON object; a token event carries the next fragment of the answer, which the client appends to the growing reply so that the answer appears to type itself, and a terminal sentinel marks the end of the stream. This streaming shape is what makes the mentor feel responsive even when the underlying model generates slowly, because the learner sees the answer begin immediately rather than waiting for it to complete.

The **mission-signal protocol** is internal to the browser rather than crossing the network, but it is a genuine protocol nonetheless and it is what makes the guided missions self-verifying. As the learner operates an exercise, the interactive widgets and the terminal dispatch a custom browser event carrying a detail object that names the lab and the kind of thing that just happened — an exploit of a particular kind, the appearance of a flag, a chunk of terminal output. The missions component listens for these events and, for the terminal, accumulates the output and tests each mission's declared detection pattern against it, ticking off any mission whose trigger matches. Because this protocol is a set of well-defined event shapes rather than ad-hoc coupling between components, the widgets and the missions do not need to know about one another directly; they communicate only through the event, which keeps the exercise components and the missions component independent.

## Chapter 30. The Content Manifest Schema

Every laboratory is a single manifest, and this chapter documents the manifest's shape precisely. The fields common to every manifest are the identifier, which must be lower-case kebab-case; the module classification of either application-security or awareness; the execution tier from zero to three; a category string; and the bilingual title and summary, each an object carrying an English and a Hindi string. From there the shape depends on the module.

An **application-security manifest** carries a lifecycle, which is an ordered list of sections. A content section carries a title and a body. An objectives section carries a title and a list of items. A code section carries a title together with an insecure and a secure code sample for side-by-side comparison. An interactive section carries a title and names the widget that implements the exercise — the SQL-injection console, the direct-object-reference console, the terminal, and so on — together with any hints. Beyond the lifecycle, the manifest carries a quiz, which is a list of questions each with a prompt and a list of answer choices; the correct answers are never present in the shipped manifest, living instead in the server-side key table. It optionally carries missions, each with an identifier, a bilingual title and hint, and an optional trigger that is either a signal token matched against the mission-signal events or a detection pattern matched against terminal output. And it optionally carries the enrichment fields that the redesigned lessons lead with: a real-world impact statement, a list of common mistakes, a list of best practices, and a mitigation checklist, each bilingual.

An **awareness manifest** carries instead a scenario graph: a named start node, and a map from node identifiers to nodes. A node has a type — narration, decision, consequence, feedback or checklist — and, according to its type, a bilingual content, prompt or title; an optional channel that tells the interface whether the beat is an SMS, a chat, a video call, a payment request or an email; an optional animation hint; for a decision node, a list of choices each with a bilingual label and the identifier of the node it leads to; for other nodes, the identifier of the next node; an optional list of red flags marking the tell-tale signs; an optional outcome classification; an optional technique explanation; and for checklist nodes, a list of items. The scenario engine walks this graph from the start node, rendering each node according to its type and following the learner's choices, and the graph's branching is what gives the awareness exercises their decision-rehearsal character.

The manifest is validated whenever it enters the system — at boot for built-in files, and on save for authored modules — against these rules: the identifier must be well-formed, the module and tier must be valid, the title and summary must carry both languages, and an awareness manifest must have a start node and a node map. A manifest that fails validation is rejected loudly rather than served broken, which is why a content error surfaces at deployment or at authoring time rather than in front of a learner.

## Chapter 31. Representative Request Sequences

To make the interaction of the parts concrete, this chapter traces the most important operations step by step.

**Logging in.** The browser submits the email and password to the login endpoint. The server looks up the user by lower-cased email, compares the password against the stored bcrypt hash with a comparison that does not reveal whether the failure was a missing user or a wrong password, and refuses a deactivated account. On success it signs a session token carrying the user's identifier and email, sets it as an HTTP-only cookie, computes the user's roles and effective permissions from the access-control tables, writes a login event to the audit log, and returns the full user. The browser stores nothing sensitive — the token is in an HTTP-only cookie it cannot read — and uses the returned permissions to decide immediately whether to reveal the administrative area.

**Entering a tier-three lab and running an exploit.** The learner opens the lab's practice mode, and the workspace mounts. Exactly once per session, it posts to the start endpoint; the server claims a Redis slot, and if the concurrency ceiling is not reached it runs a hardened container for the learner, records the container against the slot, and returns. The workspace begins sending heartbeats on an interval. The learner's browser opens the terminal WebSocket; the server authenticates the upgrade from the session cookie, confirms the learner owns the running container, allocates a pseudo-terminal and runs a shell inside the container attached to it, and begins bridging bytes. The learner types an exploit; the keystrokes travel as input frames to the pseudo-terminal, the shell executes them, and its output streams back and is both painted into the emulator and scanned for the flag and other patterns, which dispatch mission-signal events that tick off the corresponding objectives. When the learner leaves, the workspace posts to the stop endpoint after the start has completed, the server kills the container and releases the slot, and if for any reason the stop is missed, the reaper destroys the container once its idle timeout elapses.

**Submitting a quiz and earning a certificate.** The learner answers the quiz and posts their answers to the quiz endpoint. The server loads the correct answers from the key table — which the browser never saw — grades the submission, records the score, and writes a quiz-answered event. If the score meets the threshold and no certificate yet exists for this learner and lab, the server issues one idempotently, computing a keyed signature over its canonical contents and storing it. The learner can later verify the certificate through the public verification endpoint, which recomputes and checks the signature and returns the verified contents to anyone who presents the identifier, without exposing any private data.

## Chapter 32. Building, Running and Extending the Platform

The platform is brought up with a single orchestration command that starts the database, the Redis instance, the lab manager, the static web server and, under an optional profile, the local language model. On first start the database applies its schema and seed; on subsequent structural changes an idempotent migration is applied against the running database, because the initialisation scripts run only against an empty data volume. The lab manager image is built in two stages so that the native terminal addon is compiled once, against the runtime's Node version, and carried into a slim runtime image; the build runs on the host network so that the addon's compiler can fetch the correct headers, a configuration folded into the compose build definition. Because the lab manager runs the compiled build baked into its image, a change to the back-end requires rebuilding that image and recreating its container, whereas a change to a built-in content manifest, being mounted read-only, takes effect on restart without a rebuild, and an authored module takes effect immediately.

Extending the platform follows the grain of its design. A new laboratory is, in the ordinary case, a new manifest — authored in the application by an administrator, or added as a file for a built-in — validated against the schema and served through the same paths as every existing lab. A new tier-two exercise additionally needs its vulnerable behaviour implemented on the server and its per-user data table added by migration, but the pattern to follow is established by the dozen tier-two labs that already exist. A new role or an adjustment to a role's powers is a data change in the access-control tables, not a code change, because the authorization gate checks permissions that live in data. This is the disciplined extensibility that the architecture was built to provide: the common case of growing the curriculum is content work, and only the genuinely new capabilities require code.
